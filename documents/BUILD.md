# Build

**Scope:** How Noldova Desktop's tooling builds, packages, publishes and updates an app: an app's inputs, development builds, the targets and formats, the packages' contents and signatures, publication, updates, and stopping every process of an installation for an update.
The organization's security standard, `https://github.com/noldova-com/.github/blob/main/standards/SECURITY.md`, applies in full.

## The build package

- An app builds with `@noldova/desktop.build`, installed as a dev dependency, since it builds the app and doesn't ship in it, at the version of its other Noldova Desktop packages, with Electron at the version the package names as its peer, and runs the package's bin, `noldova-desktop-build`, in its own folder, usually from its own `package.json` scripts.
  Its commands, `install`, `build`, `start`, `desktop-tools`, `package`, `package-smoke`, `list-targets`, `release-check`, `release-assets` and `release-publish`, are what this document describes, and [its README](../src/noldova.desktop.build/README.md) lists their arguments.
  Its second bin, `noldova-desktop-release`, runs only `list-targets`, `release-check`, `choose-feed`, `release-publish`, `feed-check`, `module-range` and `noldova-desktop-range`, and loads only Node.js's own modules and the `@noldova` peers its `package.json` declares, which the "Release entry" check enforces, so a release job that holds a write token runs it from the package's archive with the archives of those peers, read from the archive's `package.json`, unpacked beside it, each checked against the app's lockfile, without installing anything, and fails on a peer the lockfile doesn't lock; a module's range check runs it from the archive of the Noldova Desktop version the module pins, with those peers at the versions the module's lockfile holds beside it, each checked against the SHA-512 the registry gives for it, and fails on a mismatch, as the README's "Checking a module against its range" says.
- An app's `src/` holds only package folders, and one of them is its window app, the folder whose name ends in `.window.app`, such as `src/noldova.desktop.window.app`, with the window's `angular.json`, `package.json`, `tsconfig.json`, `tsconfig.app.json` and its `src/` with `index.html` and `main.ts`; the build refuses a `src/` with two.
  The app's root `package.json` names the window app among its `workspaces`, so the app has one lockfile and one `node_modules`, at its root.
  The window app's `package.json` names Noldova Desktop's window package, `@noldova/desktop.window`, at the version of its other Noldova Desktop packages, and the kit, `@noldova/ui.components.angular`, at one exact version inside the window package's peer range, as [MODULES.md](MODULES.md#context-and-kit-versions) says, and Playwright only when an `angular.json` under `src/` has a test target.
  That `package.json` also names each Angular package the window package peers on, at the exact version it names, which npm's install needs with or without `--strict-peer-deps`: `@angular/cdk` accepts newer versions of `@angular/common`, so without them npm takes a newer `@angular/common`, whose exact peer on `@angular/core` clashes with the window package's, and stops.
  `install` installs the app with `npm ci` at its root when the root lockfile changed since its last install, and the browser for the Angular tests only for a test target, Chromium's headless shell, with `playwright install --only-shell chromium`, which the CI caches name in their keys, so a change to that set changes those keys too; it is the only command that needs the registry's token, so a CI gives the token to its step alone.
  It then runs `npm ls`, so it needs `npm_execpath` as `npm run` sets it, even when `npm ci` doesn't run.
  It fails when `npm ls @angular/cdk --all` lists more than one copy in the app, naming each copy with the packages it sits under, since the kit and the window would each run their own overlay container and focus handling.
  `build --list-copies` builds nothing and prints each file the build copies unchanged into a package and its `files` keep in the archive, the archive check of the organization's shared release workflow reads: the root `LICENSE` and the package's `README.md`, module files and `src/assets/`, its `src/api/*.d.ts` when it has no `scripts/build.ts`, and the folders its `scripts/build.ts` lists with `--inputs` when it has one, one line for each file with its source's path from the app's folder, the package's name and its path inside the package, separated by tabs, then `end of copies`, also when it copies nothing.
  `build` refuses an app that isn't installed for its current lockfile, and before it installs the Angular packages it builds, it removes only the Angular packages of Noldova Desktop and of the app's modules that the root `package-lock.json` doesn't lock, so the window package the app installs stays.
  Once it has installed them, it refuses a second copy of an Angular, Noldova Desktop, context or kit package anywhere in the app's install, and an Angular package that Noldova Desktop's runtime, Electron, command line, protocol or build package reaches, as [MODULES.md](MODULES.md#what-fails-closed) says, so the window holds the app's one copy of each and Angular stays on the window's side.
- The package takes TypeScript and electron-builder from the app's root `node_modules`, which pins them at the package's versions, as every shipped dependency is pinned in the folder that installs it; the app has one TypeScript, which the build and the window's Angular compiler both use, so the package pins the version Angular's compiler takes.
- Noldova Desktop builds itself with the same package, run from its source: its root `package.json` scripts run `src/noldova.desktop.build/src/services/build-command-line.ts`, and its `build` script, `scripts/build.ts`, runs `install` then `build` with the script's arguments, since the package builds itself, or `build --list-copies` alone, without `install`, when it is given that option, and Noldova Desktop's own scripts import the package's source until it moves to a repository of its own.
  The package's source imports its own files by their `.ts` paths, which its compilation rewrites to `.js`, so it runs from source and as published; a package test checks that the installed package imports only `.js` files.

## An app's inputs

- An app's root `package.json` declares, under `desktop`:
  - `product`, the app's identity: its name, publisher, slug, application and development application ids, data folder, device folders, data directory variable, icons folder and release repository; never the Windows publisher, which a signed build takes from the release's secrets, and a `package.json` that names `windowsPublisher` is refused;
    optionally `categories`, its macOS app category and Linux main category (`macos` and `linux`, by default `public.app-category.developer-tools` and `Development`);
    and, for an app that signs on Windows, `windowsSigning`, its Artifact Signing `endpoint`, `account` and certificate `profile`, which are no secrets;
    and optionally `permissionsModule`, the id of the module that answers permission requests and manages remembered answers, as [PERMISSIONS.md](PERMISSIONS.md#answering) says, which the build refuses unless it is one of `modules`;
    and optionally `about`, what the window's About shows of the app, each field optional: `description`, one line; `website` and `releases`, https addresses; and `licenses`, text; the build refuses a value About can't show, naming its field;
    and optionally `updateFeed`, the app's own update feed, an https folder URL ending in `/` with no user info, query or fragment, such as one that counts update checks and forwards to the release, as [Updates](#updates) says; the build refuses any other value;
  - `modules`, the modules the app includes, in a list outside Noldova Desktop's packages, so adding a module changes that list and no source of Noldova Desktop; each is a module in the app's tree or in an installed package, as [MODULES.md](MODULES.md#modules-from-packages) says;
  - `supportedTargets` and `signedPlatforms`, as below.
- Noldova Desktop's packages never spell a value of the identity in their production source: they take it from the build's product file, and the Product identity check of `npm test` refuses a value spelled there.
  The build reads the identity through `src/noldova.desktop.build/src/models/packages/product-identity.ts`, which refuses a section that is missing or has an invalid field.
- The root `package.json` also declares the app's version and, apart from it, the protocol's version.
- The app brings `LICENSE`, the icons folder its product names and `assets/dictionaries`, and packaging refuses to start without one of them.
  The icons folder holds `icon-dark.ico` for Windows, `icon-dark-512.png` for Linux and `icon-dock-512.png` for macOS, which the program file and the window take; the `dark` files are for a dark taskbar, drawn light.
  It may hold `icon-light.ico` and `icon-light-512.png`, drawn dark, which the window takes on a light taskbar, and in `tray` each state's `tray-<state>-light.ico`, `.png` and `@2x.png` beside its `tray-<state>` files, which the tray icon takes there.
  The `tray-update` files, shown while an update is ready, are optional: without them the tray shows its `tray-unread` icon then.
  The build package brings the rest under its own `assets/`: the installer's include `installer/installer.nsh`, the macOS entitlements `macos/entitlements.plist`, the fonts' licenses `licenses/fonts/` and the reviewed license texts `licenses/third-party/`.
  An app overrides one with a file at the same path under its own `assets/`; a reviewed license text is looked up in the app's folder before the package's, and the app's own font licenses ship beside the package's.
- The build is self-contained: exact pins and the lockfile describe what it installs, and no sibling checkout or copied installation is an input.
- The build writes the app's identity, its permissions module, its version, its update feed and the fingerprint of everything it was built from into one file, `_build/product.json`, at the root of the project that installs Noldova Desktop's packages.
  The runtime, the main process and the command line read it once, the first time something asks for the product or the build's identity, as each does when it starts; importing a package never reads it.
  A project that Noldova Desktop's build doesn't build, such as a module's own repository, can import the packages and run what needs neither; asking for the product or the identity there fails with a `ProductFileException` that names the missing file, and code that needs them, such as starting the runtime, needs that file at the project's root, in the form the build writes.
  The same inputs give the same fingerprint, and any change gives another, which is how the runtime's build is known.
  The build's own package is one of those inputs, and a process hashes it once, since the code it runs is already loaded; a process that runs several builds doesn't see that package replaced on disk until it restarts.
- The build checks the modules' declarations once its packages are built and installed, so a module from a package of its own is read from the installed copy, and writes what the runtime and the command line read of them to `_build/modules/declarations.json`, and generates the source that brings the window parts into the window, with the product's name and the gallery, in `_build/generated/`.
  The window app's entry, its `src/main.ts`, imports what the build generated from `../../../_build/generated/` and starts the window with it, through `WindowApplication.startAsync` from the installed `@noldova/desktop.window/build`, so the window's package is the same for every app.
  Among those inputs is `productName`, the app's `desktop.product.name`, which the build writes to `_build/generated/product.ts`; the window shows it wherever it names the app, and refuses to start without it.
  Beside it the build writes `productAbout`, the app's `desktop.product.about`, with null for each field the app leaves out, and its `logo`: once it has built the window, the build copies the icons folder's `icon-light-512.png` and `icon-dark-512.png` beside the window's files, under `browser/about/`, and `logo` names them, the dark icon for both modes when the app has no light one and null when it has no dark one.
  An entry that passes `productAbout` as `about` gets those details in About, and one that passes none gets About without them.
  The entry may also pass `providers`, which the window adds to its root injector after its own, so one replaces a window provider of the same token.
  It is for what only the app's own compiled code can make, such as a web worker, which Angular's application build bundles only from the app's code, never from a package in `node_modules`; the window names no such service itself.
  An entry never replaces the window's own: its `ErrorHandler`, whose replacement stops the window logging each error to the main process with the module whose window part failed; its `ClipboardWriter`, whose replacement copies without the main process; and the `BuildTokens` and `GalleryTokens` values, which the window fills from the entry's other inputs.
  A multi provider, such as `ENVIRONMENT_INITIALIZER`, adds to the window's own rather than replacing them.
- A test build adds Noldova Desktop's fixture modules, and nothing else depends on them.
  One of them is a module from a package: the build builds and installs its package, and lists it as `desktop.modules` lists a module from a package, at its `module.json`'s version.
  Its window part is an Angular package of its own, which the module's package pins, as [MODULES.md](MODULES.md#modules-from-packages) says; the build compiles it against the installed window package before it builds the module's package, and installs both into the app's `node_modules`, beside the window package.
- The platform and the processor are inputs too, since a package's archive can differ by both.
- The build uses the prebuilt addon a package ships for the target's platform and processor when it has one, and otherwise compiles each addon a package lists for the platform, its Windows addons on Windows and its POSIX addons elsewhere, for the machine's own processor, with the node-gyp that npm bundles; an addon uses only Node-API, so the same file runs under Node.js in the tests and under the app's program.
  It needs Python and a C toolchain: on Windows the "Desktop development with C++" workload of Visual Studio or its Build Tools, on macOS the Xcode command line tools, and on Linux a C compiler and make.
- Each addon's build goes to `native/<platform>-<arch>/<addon>.node` in its package, named by Node.js's `process.platform` and `process.arch`, such as `native/win32-arm64/windows-process.node`.
- When `RELEASE_ADDONS` names a folder, as the organization's shared npm release sets it, the build compiles no addon and copies each declared addon's builds from `RELEASE_ADDONS/<package path>/<platform>-<arch>/<addon>.node`, such as `src/noldova.desktop.runtime/linux-arm64/posix-process.node`, for each Windows addon `win32-x64` and `win32-arm64` and for each POSIX addon `linux-x64`, `linux-arm64`, `darwin-x64` and `darwin-arm64`.
  It fails when any of them is missing, naming the package, the addon and the target, and it ignores the folder's other files.
- The runtime loads the build for the platform and processor it runs on, and refuses with a message naming them when its package has no such build.

## Development builds

- A development build runs under the app's name and icon, from a copy of Electron's distribution labelled from the app's identity, never as Electron.
- It starts on `_build/development-package`, a folder whose `package.json` names the main script and carries the app's version, so Electron and the updater read the app's version, not Electron's.
- It uses `<development application id>.<checkout hash>` as its id, the hash being the first eight hexadecimal digits of the SHA-256 of the checkout's absolute path, so each checkout has its own taskbar entry and its own data directory.
- A development build never reads the production update feed.

## Targets and formats

- The targets are Windows, Linux and macOS, each on x64 and ARM64.
  `desktop.supportedTargets` lists a target, by an id such as `windows-x64`, only once its build and its native acceptance are verified: a release built, packaged and published it, and its own package passed `package-smoke` on that processor, whose program, frameworks and addons are built for that processor alone and whose app starts and answers `status` there.
  An app's release builds Linux x64, Windows x64 and the other x64 targets its `desktop.supportedTargets` lists, so leaving `macos-x64` off the list stops its packaging and signing, and putting it back restores them; an app without the field builds every x64 target.
  A left-out target's `latest-<platform>-<arch>.yml` is no longer published, so its installed builds stop finding updates until it is listed again: each automatic check keeps "The update feed answered with HTTP status 404." as its reason, and a requested check shows it as failed.
- The formats are an NSIS installer on Windows, a DMG and the ZIP its updater downloads on macOS, and an AppImage and a Debian package on Linux.
  electron-builder 26 makes the DMG with dmgbuild, whose command line tries 5 times, about 20 seconds, to detach the image's volume, while macOS can hold it busy for longer, so a macOS build whose electron-builder fails with dmgbuild's "Unable to detach device cleanly" runs electron-builder once more, saying so; any other failure, a second one, or another target's fails at once.
  The Debian package installs into `/opt/<app name>/`, links `/usr/bin/<slug>` to its program, and keeps Chromium's sandbox on without any change to the kernel's settings: electron-builder's after-install script makes `chrome-sandbox` setuid root, mode 4755, where root can't create a user namespace and leaves it 755 where it can, and, where AppArmor is enabled and takes the profile, installs `/etc/apparmor.d/<slug>`, which allows the program user namespaces and is loaded at once; the package's `homepage` is the product's website, or its release repository on GitHub, and its maintainer the product's publisher.
  An AppImage can't carry Chromium's setuid sandbox helper, so its launcher tries `unshare -Ur true` and starts the app with `--no-sandbox` when that fails: on a host that refuses unprivileged user namespaces, as Ubuntu 24.04 and later do by default, in a container that refuses them, or where `unshare` is missing.
  The app's renderers then run without Chromium's sandbox, as [ARCHITECTURE.md](ARCHITECTURE.md#code) says; where the probe succeeds, they run sandboxed, and the Debian package runs them sandboxed on such hosts too.
  After packaging for macOS, signed or not, `package` extracts the ZIP with `ditto -x -k`, as Squirrel.Mac does, and fails unless each framework's `Versions/Current` is still a link and the extracted app holds the same folders, links and file sizes as the packaged one.
- A download is named `<app name>-<version>-<platform>-<arch>.<ext>`, such as `Sample App-1.2.3-windows-x64.exe`, with the version the package was built as, and its checksum `<download>.sha256`, so releases' files kept side by side never share a name.
  The update information keeps its one name per target, `latest-<platform>-<arch>.yml`, since an installed app reads it to learn the newest version, and it names the versioned package to download.
  An update replaces an AppImage in place, under the name it was downloaded with, so a launcher or shortcut that points at it keeps working.

## Packaging

Each target is packaged on its own platform and processor, through electron-builder.

- **Layout:** the packaged app mirrors a checkout's layout inside `resources/app.asar`, so the main process, the runtime and the command line find their files by the same relative paths; only native files and the files packages name are unpacked, into `resources/app.asar.unpacked`, where the system and other programs can load, run or read them.
  A package's addons for other targets stay out of the package: the stage removes each installed package's `native/<platform>-<arch>/` and `prebuilds/<platform>-<arch>/` folders but the target's own, named by Node.js's platform and processor, since a published package such as `@noldova/desktop.runtime` or node-pty carries every target's build, and the stage's log names what it left out.
  The same goes for node-pty's ConPTY builds: the stage keeps only `third_party/conpty/<version>/win10-<arch>/` for a Windows target's processor, and none for macOS or Linux.
  Otherwise a Windows x64 package would carry the ARM64 `OpenConsole.exe`, and package-smoke would check it.
  The native files are each `.node` addon and every other file of the staged app whose header names a native program or library, a Windows PE file, an ELF file or a Mach-O file, such as node-pty's `conpty.dll` and `OpenConsole.exe` on Windows and its `spawn-helper` on macOS.
  The named files are those an installed package's `package.json` lists under `noldovaDesktop.unpacked`, as [MODULES.md](MODULES.md#files-other-programs-read) says, in any package of the stage, nested ones too.
  electron-builder lays `node_modules` out again from its own hoisted dependency graph rather than as the stage has it, and matches `asarUnpack` against each file's path in `app.asar`, so a nested package with no version conflict lands at the top and a top-level one can land nested.
  So a file of a package is written to `asarUnpack` as a pattern that holds no path of the package, `**/node_modules/` then the package's name and the file's path inside it, such as `**/node_modules/inner/bin/helper` for the stage's `node_modules/host/node_modules/inner/bin/helper`, and electron-builder unpacks it wherever it puts the package; a file of the app's own is written by its path.
  The native files listed are only those electron-builder ships for the target, by rules copied from electron-builder 26.16.1's own filter, which it doesn't export.
  A packaging spec packages one file of each kind on each target and fails when electron-builder ships or leaves one out differently, so an electron-builder update that changes its filter shows there first.
  On macOS and Linux it never ships a package's `.exe` or `.dll`, so node-pty's Windows programs and libraries stay out of those lists.
  On every target it never ships what it always leaves out: `.pdb`, `.o`, `.obj` and `.a` files, files whose names start with `._`, and a package's top-level `test`, `tests`, `__tests__`, `example` and `examples` folders, among others.
  A native file of another platform that ships stays unpacked, such as node-pty's macOS `spawn-helper` in a Linux package.
  Packaging refuses a native file whose path holds a character a file pattern reads as a wildcard, since electron-builder takes the list as patterns.
  It refuses a named file, naming the package and the path, whose path holds such a character, is absolute, has an empty, `.` or `..` segment, or goes into `node_modules`, where other packages are; whose folders or name differ in case from the package's own, since the patterns match case exactly; that a symbolic link on its path takes outside the package's own files; that the package names twice, by the same path or through a link; that the package doesn't hold; or that electron-builder ships on no target, naming the rule that leaves it out.
  A named `.exe` or `.dll` is listed for Windows only, since electron-builder ships a package's `.exe` and `.dll` files on Windows only.
  `package-smoke` then checks the installed package: each exact path of the configuration's `asarUnpack`, and each path in `app.asar` that a package's pattern matches, is in `app.asar.unpacked`, marked unpacked in the archive's header, and readable with a plain file read; a package's pattern that matches no entry of `app.asar` fails it, and the smoke reports the packaged paths it checked.
  On macOS it also reads the header of every file in the app bundle, nested apps and frameworks, their libraries and helpers, and `app.asar.unpacked` included, following no link, and fails on any Mach-O file not built for the target's processor alone, so a package never runs under Rosetta or carries a universal, 32-bit or foreign file.
  Unpacked files sit outside the archive's integrity check, which covers only `app.asar`: they are as safe as the app's folder, and on macOS the app's signature seals them.
- **AppImage runtime:** packaging pins electron-builder's AppImage toolset 1.0.3, whose runtime is the type2 AppImage runtime of `appimage-tools-runtime-20251108` in electron-builder-binaries' `appimage@1.0.3` release.
  The runtime's launch on Linux relies on its `--appimage-mount`, which prints the mount's folder and keeps the mount while its keepalive pipe has a reader ([RUNTIME.md](RUNTIME.md#starting-a-runtime)), so a new toolset is taken only once `npm run package:smoke` passes with it on Linux, which checks that the runtime's mount outlives the main process and ends with the runtime.
  A runtime that stops as the main process quits can lose its mount before its process is gone, since the system closes an exiting process's descriptors first; it withdraws its discovery file before it exits, so the smoke takes a mount that ended while the runtime still answers only once that file no longer names the runtime, and fails at once otherwise, as it does when the main process was killed.
- **Third-party packages:** a shipped package pins each third-party dependency exactly, as the root `package.json` does, so the root lockfile locks the whole tree.
  Packaging takes each tarball from the lockfile's address, checks its SHA-512 against the lockfile's integrity, and installs offline; dev and peer dependencies never ship, and a package needed in two versions fails packaging.
  That install passes npm's `--legacy-peer-deps`, so npm resolves and writes no peer, while every dependency still has to come from the build's archives: npm resolves a peer even when told to leave it out, and offline it can find only the peers the build ships, never Electron, the electron package's peer, which is the app's runtime rather than a package it ships, or a type-only peer, which is never loaded.
  Packaging checks each required peer itself, as below, and ships the context packages it needs as plain dependencies.
  The install applies the `overrides` of the root `package.json` as the app wrote them, but for the reference below, so a dependent whose own range the app overrides gets the one version the lockfile holds; the stage refuses `overrides` that are not an object.
  An override of a shipped package may be top-level or nested under the dependent it is for: the stage installs each shipped package from its archive as a direct dependency, and npm refuses a top-level override of a direct dependency unless it refers to that dependency, so the stage writes a top-level override of a shipped package, or its `.` entry, as `$<name>`, and every dependent takes the one version the archive holds.
  A `$<name>` reference in a nested override resolves against the stage's own dependencies, the shipped packages, not against the app's root dependencies.
  Its checks of a tarball's scripts and license read its files, contiguous ones included, and packaging warns of each link or other entry they skip.
  A required peer, of a third-party package or of one of the app's own, that no shipped package brings fails packaging, unless the app names it in `desktop.packaging.typeOnlyPeers`, which maps a package, as `<name>@<version>`, to `{ "peers": [...], "reason": "..." }` for peers it names only in its type declarations and never loads; packaging lists the peers it passed over, and refuses a third-party package whose `.js`, `.cjs` or `.mjs` files require or import one of them by its literal name, so a new version is checked again.
  That check sees only literal loads: a require through a variable or an alias, `createRequire`, a name built from strings, a comment before the parenthesis or a script with another extension goes unseen, so the reason must still hold.
  An optional dependency that fits the target ships, unless the app names it in `desktop.packaging.omittedOptionals`, which maps a package, as `<name>@<version>`, to `{ "dependencies": [...], "reason": "..." }` for optional dependencies the app never loads, such as a bundled program when the app starts the one the person installed.
  Packaging leaves out only those, for that version only, and lists each one that fits the target and that no other shipped package brings, so a name another package needs still ships; it refuses a name that is not one of that package's optional dependencies, so a required dependency never goes.
  It can't check that nothing loads what it left out, so the reason must hold; a package that loads one fails only when it tries.
  Packaging warns of an entry, here, in `omittedOptionals` or in `acceptedLicenses`, that names a version the app does not ship, and a refusal names the versions the app's entries cover.
  The build package's dependencies build the app and never ship in it, so the root pins each in its `devDependencies` at the package's version, and the Dependency pins check holds a package with a `bin` to that.
- **The company's packages:** a shipped `@noldova/*` package from another repository, such as context's, is the company's own, not a third party's.
  Packaging packs it from the root `node_modules`, which `npm ci` installed after checking it against the lockfile's integrity, so it needs no registry token; it must be the version the lockfile locks.
  Noldova Desktop's packages take context's packages as peers, as [MODULES.md](MODULES.md#context-and-kit-versions) says, so packaging ships each context package that a shipped package takes as a required peer, from the root's install, where the app pins it.
  An app whose `src/` holds no `@noldova/desktop.electron` or `@noldova/desktop.cli` ships the installed ones, and lists them with its module packages in the staged `package.json`.
  A company package that the app installs from an archive of its own, which its lockfile leaves out, ships only as `node_modules/.package-lock.json` records it: from a `file:` archive whose SHA-512 still matches the integrity npm recorded, and never when that record is missing.
  A module package's window part package is built into the window, so it and what it alone needs never ship: packaging packs the module package without that one dependency, from the files of its verified archive when the app installed it from one, so what ships is what npm checked.
  Packaging refuses such an archive when a header's checksum or size is wrong, an entry runs past its end, it lacks its closing block, it holds anything but files and folders, or a path leaves the package's folder, is one Windows reads differently or refuses, such as `con.js`, `CONIN$`, `COM¹`, a trailing dot or space, a control character or one of `\:*?"<>|`, or it or one of its folders differs from another only in case or Unicode form.
- **Licenses:** each shipped third-party package's license must be MIT, ISC, BSD-2-Clause, BSD-3-Clause, Apache-2.0, 0BSD, BlueOak-1.0.0, Python-2.0 or Unlicense, or an `OR` expression with one of them, and its tarball must hold its license file; the app ships every license it owes.
  A package whose tarball holds no license file ships a reviewed license text instead, `licenses/third-party/<name>-<version>.txt` with a scope's `/` written `+`, and packaging refuses the package when neither the app nor the build package holds one.
  A reviewed text covers one version alone, so a new version needs its own.
  The build package holds the texts for `@xterm/addon-serialize` 0.14.0, `@xterm/headless` 6.0.0 and `standardwebhooks` 1.1.1, each the license file of the package's upstream source at the commit its version was published from, unchanged.
  It also holds one for `lazy-val` 1.0.5, whose source has no license file: that text is the MIT License with the author its `package.json` names.
  An app may accept another license for one package in `desktop.packaging.acceptedLicenses`, which maps the package, as `<name>@<version>`, to `{ "license": "...", "reason": "..." }`; packaging accepts only that exact license string for that version, so a new version is refused until the app accepts it again, ships the file a `SEE LICENSE IN <file>` license names as the package's notice, and lists the licenses it accepted.
- **Fuses:** the program's Electron fuses allow only what the app uses:

  | Fuse | Setting | Reason |
  |---|---|---|
  | RunAsNode | on | The runtime and the command line run on the program in Node mode. |
  | GrantFileProtocolExtraPrivileges | on | The window loads its scripts from `file://`. |
  | OnlyLoadAppFromAsar, EmbeddedAsarIntegrityValidation | on | The program runs only its own `app.asar`, and on Windows and macOS refuses one that was changed. |
  | NodeOptions, NodeCliInspectArguments | off | No variable or argument changes how its Node runs. |
  | CookieEncryption | off, or on for an app with a module that declares `webViews.json` | The window loads from `file://` and signs in nowhere; web views keep their profiles' cookies encrypted, as [WEB-VIEWS.md](WEB-VIEWS.md#the-hosts-defaults) says, and `package-smoke` checks the installed program's fuse. |
  | LoadBrowserProcessSpecificV8Snapshot | off | The program has no snapshot of its own. |

- **Tools:** electron-builder's packaging tools are downloaded once and each is checked against the SHA-256 it pins.
  `package-app.yml` keeps them, the package's `_build/package/tool-cache`, in GitHub's cache between runs, keyed on the runner's OS, the architecture and the app's electron-builder version; on a miss it downloads, in a step of their own first, the AppImage tools and fpm, which builds the Debian package, on Linux and the icons tools and 7-Zip on macOS, up to 4 attempts 30 seconds apart, so a short outage of GitHub's release downloads doesn't fail the package; macOS's dmgbuild, whose getter electron-builder doesn't export, and Windows's tools, left out for now though electron-builder exports their getters, still download inside the packaging, with electron-builder's own 4 attempts, until the cache holds them.
- **Installation:** the Windows installer installs for the current user without elevation, keeps the data directory when the app is uninstalled, and puts the app's command on the user's PATH; on macOS the bundle holds the command, which the app links into `/usr/local/bin` only when the person asks.
- **Signing:** a signed package is signed on Windows with the publisher's certificate through a signing service, and on macOS with a Developer ID certificate, notarized and stapled.
  Packaging takes the signing credentials out of its own environment as it starts, gives them only to the signing step, and checks every signature it made before it reports the package signed.
  Windows signing takes its endpoint, account and certificate profile from `desktop.product.windowsSigning` and refuses to start without them; the credentials are the Azure service principal's.
  It takes the publisher, the distinguished name of the certificate's subject, from `WINDOWS_PUBLISHER`, refuses to start without it, checks every signature against it, and writes it into the packaged app's product file; an unsigned package's product file has no publisher.
  Each program and addon is signed with the certificate and must carry the publisher's signature.
  Programs, libraries and addons are told apart by their extension in any case, so an `.EXE`, `.DLL` or `.NODE` is signed and checked like an `.exe`, `.dll` or `.node`.
  A library, a `.dll` or a program a third-party package brings under `resources/app.asar.unpacked/node_modules`, such as node-pty's `OpenConsole.exe`, keeps a valid signature it already has and is signed otherwise, so a vendor's program is never signed again with the publisher's certificate.
  The check accepts a `.dll` signed by the publisher or by Microsoft Corporation, and a program a package brings signed by the publisher or by a vendor on a short list, matched on the certificate's organization: Microsoft Corporation, for node-pty's `OpenConsole.exe`, and Git for Windows' signer, for the programs of a package that bundles Git for Windows; every other signer is refused, so no other publisher's file ships.
  Neither the publisher nor a signer's subject is ever printed, so a job's log can't show the secret: the check prints each file's signature status, whether it is timestamped, and whether it is signed by the publisher, by a vendor on the list, by another signer or by no one, and a failure lists each refused file that way; and `package-smoke` checks the installed product file's publisher against `WINDOWS_PUBLISHER`, or that it has none when the variable is not set, saying only whether it is set, missing or differs.
  A notarized disk image gets its ticket with `xcrun stapler staple`, and a signed macOS disk image and each app in a package are checked with `codesign`, `spctl` and `xcrun stapler validate`.
  `stapler staple` and `stapler validate` both ask Apple's ticket service, so when their output shows a network error (`NSURLErrorDomain`) they are tried again, up to 3 attempts 5 seconds apart, and any other failure, such as a missing ticket, fails the package at once.
  Linux packages are not signed.

## Publication

- An app publishes an immutable, reviewed revision with a matching version, its packages for each target, a SHA-256 checksum for each, and its update information.
- An app releases from its own `workflow_dispatch` workflow on main, which calls Noldova Desktop's `.github/workflows/release-app.yml` at a full commit SHA with the app's folder, the version and the revision, passes the nine signing secrets by name, `WINDOWS_PUBLISHER` among them, never `secrets: inherit`, and grants `actions: read` and `contents: write`.
  An app that installs from a private registry names it with `registry-url` and `registry-scope`, and passes its token as the secret `REGISTRY_TOKEN`.
  A release's runners are the inputs `runs-on-linux-x64`, `runs-on-linux-arm64`, `runs-on-windows-x64`, `runs-on-windows-arm64`, `runs-on-macos-x64` and `runs-on-macos-arm64`, each as the JSON `runs-on` takes; each defaults to `default`, the organization's runner from its `versions.yml`, and an empty ARM64 input leaves that target out.
  For Linux and Windows ARM64, `versions.yml` names GitHub's hosted runners only to a public caller or one whose `RUNNER_TYPE` is `GITHUB`; a private caller on self-hosted runners gets no ARM64 runner unless the organization sets `RUNS_ON_SELF_HOSTED_LINUX_ARM64` and `RUNS_ON_SELF_HOSTED_WINDOWS_ARM64`, or the caller passes the inputs.
  It uses the environments `release` and `publish` of the app's repository, or those its `signing-environment` and `publish-environment` name.
  - Before a release is started, the maintainer runs the macOS x64 start check below from a checkout of the revision the release takes, and it must pass; the release's own macOS x64 job skips that check.
  - Its `fetch` job refuses a revision that is not a full commit SHA on main, then takes desktop.build's archive at the version the app's `package-lock.json` locks, from the npm registry, and checks its SHA-512 against the lockfile.
    It then reads the `@noldova/*` names among the archive's `peerDependencies`, and takes and checks each of those packages the same way, at the version the lockfile locks; a peer the lockfile doesn't lock fails the job with its name.
    It passes that list on as its `peers` output, so the later jobs check and unpack the same packages, a job without a checkout against the SHA-512s the `fetch` job checked.
  - Its `check` and `publish` jobs check those archives again and run its release entry with no install, so no third-party code runs where `contents: write` is held.
  - Its `build` and `build-signed` jobs call `$/.github/workflows/package-app.yml`, Noldova Desktop's own file at the commit the app calls; only `build-signed` runs in the environment `signing-environment` names, `release` by default, from main, with the signing secrets, and only `publish` runs in the environment `publish-environment` names, `publish` by default.
- `package-app.yml` installs the app's dependencies and runs its `prepare` command with install scripts off, so npm runs no dependency's install script in either, and no pre- or post-script of a script `prepare` runs.
  Since that also skips the app's own root lifecycle, the install then runs the root package's `preinstall`, `install`, `postinstall`, `prepublish`, `preprepare`, `prepare` and `postprepare` scripts by name, in npm's order, as `npm ci` would; one that installs another folder, such as `npm ci --prefix src`, runs no dependency's install script either.
  Electron's binary installs in a step of its own.
- Noldova Desktop ships no installers of its own; its CI packages its own app unsigned through `package-app.yml` on each target that has a runner variable, as `list-targets` lists them for a release: every one but macOS x64 for a pull request, draft or ready, or a run started by hand, since the organization has one macOS x64 runner, and every one on main; it installs, starts and quits the app on each but macOS x64, as below, and `package-app.yml` never signs there.
  Once the started app answers `status --json`, the smoke checks that every module `desktop.modules` lists is in its `modules` and `Active`, or `Unavailable` on a platform the module's `platforms` leave out, or `Blocked` when one of its dependencies, followed down the chain, is a module that platform leaves out, or `Off` when the module declares a `switchSetting`, which can be off by default; it then waits up to a minute for its `window` to be shown, with its page painted, and titled with the product's name, or with a page's title, a dash and the product's name, as `<page> — <product>`, which the window shows while a page is open, and stops at once if the main process exits.
  It fails naming each missing or inactive module with its state and cause, or the window's title, or that it is hidden or shown with its page unpainted, with the main process's ending or the last `status --json` exit code and text, and the logs' tail.
- A macOS x64 runner may have no window server, so `package-app.yml` builds and packages macOS x64 there, in CI and in a release, but skips its install, start and quit.
  The maintainer runs that check on an x64 Mac with a desktop session, from a checkout of the revision: `npm run package && npm run package:smoke`.
  It runs for each main revision a release takes, before the release, and whenever a change touches packaging or the app's start on macOS.
- A Windows package's smoke first removes what an earlier run left installed, its install folder and its command on the user's Path, and `package-app.yml` removes it again after a smoke that failed or was cancelled, with `package-smoke --remove-leftover`, so a later run on that runner starts clean.
- `package-app.yml` keeps a run's release files as the `release-<platform>-<architecture>` artifact only when its caller sets `keep-release-files`, as `release-app.yml` does for every release and test of updating, which its publish job takes; a pull request's run keeps none unless its caller asks.
  Every run, kept or not, fails when its release files lack a package, a package's checksum or the update information.
  Every run keeps its `report-<platform>-<architecture>` artifact; both last 14 days for a run of a given revision, such as a release's, and 1 day for any other.
- On Linux, `package:smoke` checks Chromium's sandbox from `/proc` once the window is shown, choosing as the launcher does, by whether `unshare -Ur true` succeeds, and saying so when the `/proc/sys` settings for user namespaces disagree with that probe; `--require-fallback` skips the probe and requires the start without the sandbox.
  Where the probe succeeds, the main process must run without `--no-sandbox` and every renderer under a seccomp filter, mode 2, within 5 seconds, since a renderer still starting may not have set its filter yet; where it fails, the main process must run with `--no-sandbox`.
  Either way it prints each child process's type and seccomp mode; a seccomp filter alone doesn't show the sandbox is on, since a renderer can have one under `--no-sandbox` too.
- `package:smoke --deb` installs the Debian package with `sudo --non-interactive apt-get install`, finds its program through `/usr/bin/<slug>`, and checks that `chrome-sandbox` and the AppArmor profile are what the after-install script leaves on that host: the helper's owner and mode against whether root creates a user namespace, as the script's own test does, and the profile copied and loaded where `apparmor_parser` takes it, or absent where AppArmor is off or refuses it.
  It then smokes the installed app as it does the AppImage, requiring the sandbox unless given `--no-sandbox` or `--require-fallback`, and removes the package with `apt-get remove`, failing when its folder or profile is left; a smoke that fails removes it too.
  `package-app.yml` changes no kernel setting: on Linux it runs the Debian package's smoke with `--require-sandbox` on the default `ubuntu-24.04`, which refuses unprivileged user namespaces, so the sandbox it proves is the one users get from the package.
  It then smokes the AppImage on its mount with `--require-fallback` where `kernel.apparmor_restrict_unprivileged_userns` is 1, and with the probe elsewhere, and the extract-and-run AppImage with `--no-sandbox`.
- On Linux, `package-app.yml` runs `package:smoke` on the AppImage's mount, then with extract-and-run, whose extraction of about 300 MB goes to the job's temporary folder: the smoke kills the main process, so the AppImage runtime never removes it.
  The smoke fails if its extraction isn't there, and a step that always runs removes it, fails the job if `/tmp` holds an extraction of the same name, and only warns of others, which other jobs on the machine may have left.
- `desktop.signedPlatforms` declares the platforms whose packages are signed, and a release to the app's update feed is refused while it leaves Windows or macOS out.
- A release's jobs run on the runners its caller names in its `runs-on-*` inputs, by default the organization's runners from its `versions.yml`, which `list-targets` reads as `RUNS_ON_<OS>`, where `<OS>` is `LINUX`, `WINDOWS` or `MACOS`.
  An ARM64 target builds whenever its `RUNS_ON_<OS>_ARM64` variable is set, and a release refuses to start when the variable of an x64 target it builds names no runner.
  The defaults set each ARM64 target's for which the organization has a runner: for a public caller, or one whose `RUNNER_TYPE` is `GITHUB`, GitHub's hosted `ubuntu-24.04-arm` and `windows-11-arm` for Linux and Windows, so its release builds all six targets unless it empties an ARM64 input.
  A private caller on self-hosted runners builds Linux and Windows ARM64 only where `RUNS_ON_SELF_HOSTED_LINUX_ARM64` and `RUNS_ON_SELF_HOSTED_WINDOWS_ARM64` name runners, or its caller passes the inputs.
  The release's `check` job gives its publish job the ids of the targets it listed as `RELEASE_TARGETS`, such as `linux-x64,windows-x64,macos-x64,macos-arm64`; `release-publish` refuses an empty, repeated or unknown id, a list without Linux x64, Windows x64 or an x64 target the app's `desktop.supportedTargets` lists, or without every x64 target when the app has no such field, and a `desktop.supportedTargets` entry the release did not build.
  It then requires exactly those targets' package reports, packages, checksums and update information, and its notes name those targets alone, so a release without ARM64 targets publishes and says so.
- Build jobs get no publishing rights; only the packaging step of a platform the release signs gets signing credentials, and publication refuses a package whose signing differs from the declaration.
- Publication takes the exact files that the release's own run built and checked, retries an upload at most three times, and never silently replaces a published tag or file.
- Versions are `major.minor.patch`, with no prerelease suffix, each higher than every version already published, tagged `v<version>`; each publication becomes the latest release.
- A `v<version>` tag already on the release's commit is kept and the release goes on, so an app whose packages' release tags the same `v<version>` can run either release first; a tag on another commit refuses the release.
- A release to any repository other than the app's release repository is an unsigned test release, which says so and never reaches the update feed.
- An app may publish in a repository other than its source, such as one shared by several apps, with `release-app.yml`'s `release-repository`, and tag its releases `<prefix><version>` with `release-tag-prefix`, such as `app-0.0.2`; both default to the app's own repository and `v`.
  - `release-check` then reads the revision, its comparison with `main` and its Build and test run in the source repository.
    It compares the version only with that repository's releases under the app's own prefix, refuses a tag that already exists there, and refuses an app whose `desktop.product.updateFeed` is unset, since that repository's latest release may be another app's.
  - The draft names no commit and its name is the tag; GitHub makes the tag at that repository's default branch when the release publishes, and publication then requires the tag rather than a commit.
    The notes end with the source repository and commit, and when the release runs in a repository that is neither the source nor the release repository, they leave out the link to its run, which may be private.
  - `release-tag-prefix` must name the app there, such as `app-`; `v` is refused, since a `v` tag in a shared repository can't say which app it belongs to.
  - The release is still marked as that repository's latest, so its latest release is whichever app published last.
    An installed app reads its own `desktop.product.updateFeed`, never that repository's latest; before a second app publishes there, every app's feed must resolve its newest release by the app's own prefix.
  - Publishing there needs a token that may write that repository's releases, since the run's own token writes only the repository running it.
    The `publish` job creates it with `actions/create-github-app-token` from a GitHub App installed on that repository, limited to it and to Contents write, whose client ID is the variable `RELEASE_APP_CLIENT_ID` and private key the secret `RELEASE_APP_PRIVATE_KEY` of `publish-environment`.
- An app's official build may run in another repository, such as a private one that builds several apps, with `release-app.yml`'s `source-repository`; it defaults to the repository running the release.
  - Every job checks out `source-repository` at `revision` and builds `app-folder` from it, and `release-check` reads the revision, its comparison with `main` and its Build and test run there.
  - The source must be public: the release reads it with the run's own token, which reads no other private repository, and `release-check` refuses a private or missing source before anything else there.
  - `signing-environment` names the environment of the repository running the release whose secrets sign the packages, such as one per app.
- `feed-check` checks a published update feed as an installed app reads it, anonymously: for each target it reads `latest-<platform>-<architecture>.yml` and requires the release's version, then downloads every file it lists and requires its SHA-512 and size.
  It reads the latest release of a repository, or a feed URL it is given, which must carry no user info, query or fragment, so no secret reaches a request or the log.
  While a target's update information is missing or names another version, as from a CDN still serving the release before, it tries again every 15 seconds for up to 10 minutes by default; any other failure, such as a package whose SHA-512 differs, ends the check at once, and its downloads together get at most 10 minutes past that wait.
  It follows a redirect only within the feed's origin or to GitHub's release asset host, and refuses a file that leads to a web page, such as a sign-in page.
  An app whose releases its installed copies can't read yet sets `skip-feed-check` to true in its call of `release-app.yml`, which passes it as `SKIP_FEED_CHECK`, and the check then says so and checks nothing; it is false by default.
  After a release publishes, `release-app.yml`'s `feed` job runs it on the app's `desktop.product.updateFeed`, which `release-check` gives as its `product-feed` output in the app's release repository alone, or else on the repository's latest release, with no permissions, passing no token to any step, from a desktop.build archive it checks against the SHA-512 the `fetch` job checked.
  The job shares `publish`'s concurrency group, so the next release publishes only once this check ends, and the latest release is still the one it checks.
  A failed check fails the caller's release job after the release is public, so the caller's jobs that need it, such as a copy to an internal feed, run only once a rerun of the failed jobs passes: a feed that installed apps cannot read is looked at first.
- A test of updating sets `update-feed` to a loopback URL, such as `http://127.0.0.1:47325/`, and may set `package-version` newer than the app's.
  `package-app.yml` then packages with that feed, `release-assets --update-feed <the loopback URL>` writes the checksums and update information against it, and the run keeps them as its artifacts; a `release-app.yml` run with `update-feed` set builds and signs as a release does, but never starts its publish job, and `release-publish` refuses to publish with `RELEASE_UPDATE_FEED` set.
  An app installs an older build with the loopback feed and serves a newer build's update information and package at that URL to test updating, on Windows and macOS between signed builds.
- Until an app's public release, its releases may also reach an internal update feed, an HTTPS folder that the input `internal-feed-url` names, so installed builds update themselves as users' will.
  - A `release-app.yml` run with `internal-feed: build`, from the app's release repository alone, which signs Windows and macOS, packages with that feed as version `X.Y.Z-internal.<run number>`, where `X.Y.Z` is the release's version, the app manifest's next release, so each internal build sorts before it, and signs as a release does; it runs on a run's first attempt only, since a re-run would build other packages under the same version; `package-app.yml` and `release-assets` accept that HTTPS feed and version.
  - `choose-feed` makes these choices for `release-app.yml`, and refuses an `internal-feed` other than empty, `build` or `copy`, an internal release with `update-feed` or `package-version`, and a `build` without `internal-feed-url`, without Windows and macOS signing, or on a re-run.
  - It never starts its publish job: its `internal` job runs `release-publish` with `RELEASE_INTERNAL_VERSION`, which checks the package reports, packages, checksums and update information for that version as a release does, makes no tag and no GitHub release, and keeps the files as the `internal-feed` artifact.
  - A run with `internal-feed: copy` publishes as usual and keeps the published files as that artifact too, so builds installed from the internal feed, whose versions sort before the release's, update to it and follow the public feed from then on.
  - The app's own workflow writes the feed, in a job defined in that workflow, after the release's jobs: only a runner group that admits that workflow alone reaches the feed's folder, which takes the packages and checksums first and the `latest-*.yml` files last.

## Updates

The main process owns updates: it checks, downloads, validates and installs, and the window shows the update's state.

- **Feed:** the update information for the main process's own target, `latest-<platform>-<architecture>.yml`, and the package it lists, over anonymous HTTPS; no credential is put in the app.
  The feed is the app's `desktop.product.updateFeed` when it names one, and otherwise the latest release of the app's release repository.
- **What a request sends:** each update request goes only to the feed's origin or GitHub's release asset host, a redirect's next request too; anything else is cancelled, and the main process's log names its host alone.
  Its User-Agent names the app's slug, version, platform and architecture, such as `sample-app/1.2.3 (win32; x64)`; of the request's other headers only `Accept`, `Range` and `Cache-Control` are sent, with the transport headers `Host`, `Connection` and `Accept-Encoding`, so it carries no cookie, not even one the feed set, no referrer, authorization or language, and no install identifier, account or path; the update specs check this on the update information requests a real session sends, on every platform, the Linux development app run with `APPIMAGE` set so that electron-updater asks the feed.
  The guard is installed on the updater's session before its first request goes out.
  The first update request of each day, by the app's local date, adds `daily`, as in `sample-app/1.2.3 (win32; x64; daily)`, so a feed can count the copies in use and not only the checks; the installation keeps only the date of its last marked request, in `last-daily-update-check`, read again before every request so the main processes that take turns checking mark one request a day between them.
  The date is recorded once the marked request's response starts; when that request fails, as when the app starts offline, the day's next request carries `daily` instead.
- **Which builds read it:** the build decides, never a setting, a variable or an argument.
  Only a packaged build names the production feed; a test build may name a local feed given to its build.
- **Versions:** only a version higher than the installed one is offered, and only `X.Y.Z` or an internal build's `X.Y.Z-internal.N`, which sorts after the release before it and before `X.Y.Z`; any other suffix is never offered.
- **Checks:** the device setting `desktop.updateChecks` chooses Automatically, the default, Only at start or Only when I ask; one main process of an installation checks at a time.
  Automatically checks 30 seconds after the main process starts and then every 10 minutes, and a check the person asks for moves the next automatic one 10 minutes on; Only at start checks once, 30 seconds after the start.
- **Validation:** before downloading, the main process checks the release's information; after downloading, the file's size and SHA-512, and on Windows a valid signature by the app's publisher and no one else, read from the app's own product file; an unsigned build has no publisher there, so it installs no Windows update.
  A file that fails is deleted and the reason shown.
- **The person decides:** a downloaded update stays ready across restarts until the person chooses Restart to update, in the window's status bar or the tray's menu, as [WINDOW.md](WINDOW.md#tray) says; closing the app never installs one.
- **Handoff:** each platform installs its own way: the Windows installer runs quietly in the existing installation's scope, macOS installs from the ZIP through Squirrel.Mac, and Linux replaces the AppImage in place with a whole new file.
  A copy installed from the Debian package, whose `resources/package-type` beside the program holds `deb`, downloads the `.deb` through electron-updater's `DebUpdater` and installs it with `pkexec /usr/bin/dpkg --install`, which asks for an administrator's permission; without pkexec it checks but never installs, and says why.
  Right before it, the file's size, SHA-512 and, on Windows, its publisher are checked again.
- **macOS location:** an app outside an Applications folder checks but never downloads or installs, and says to move it.
- **Restart:** the new version runs on the same data directory, profile and device folders as the old one.
  Only Linux restarts through a shell: started before the handoff, it starts the replaced AppImage, or the Debian package's program, once the old main process has ended, checked by process id and start time in `/proc`, since that process still holds the data directory's single-instance lock.
  It waits at most a minute, timed from its own start just before the handoff, and then writes to `logs/update-restart.log` that the old main process had not ended and starts the AppImage anyway.
- **Single instance:** a main process that finds another one holding its data directory quits and adds a line saying so at the end of that one's `logs/main.log`.

## Stopping for an update

An installation is one copy of the app's program, the AppImage file or the Debian package's program on Linux, and every main process, runtime and command line started from it belongs to it.
Before the handoff replaces its files, every process of the installation stops with its unsaved state saved, and each stop is verified, never assumed from an answer.

- **Installation record:** each installation has a folder in the device folder, named from the SHA-256 of the program's real path, which lists the data directories its runtimes have owned and the main processes running from it.
- **Launch barrier:** the installation's `barrier.json` names the main process coordinating the update, the version being installed, and the state `Preparing`, `Closing` or `HandedOff`.
  While it holds, no runtime starts, a starting main process says that the app is installing an update and exits, and the command line waits.
  A barrier whose holder has gone is settled by the next main process or command line; a `HandedOff` barrier for another version is removed only when the person confirms.
  A main process whose runtime stopped for an update that then ended without it reconnects: it checks each time the installation's folder changes, and every second, since the holder can end without changing the barrier and Node can't wait for the exit of a process it didn't start.
- **Order:** the main process where the person chose Restart to update connects to the runtime of every data directory in the record, then:
  1. asks the person about work in progress, if any, and while they wait reads it again each time a runtime announces a change of its work or disconnects;
  2. creates the barrier and asks each runtime to prepare with `desktop.update`, so no new client or program starts;
  3. waits up to 6 seconds for every client to save;
  4. asks each runtime to stop, stopping only the work the person agreed to stop;
  5. waits for every runtime and program to exit, checked by process id and start time;
  6. backs up the databases of every data directory in the record, as [RUNTIME.md](RUNTIME.md) says;
  7. waits for the installation's other main processes to exit, checked the same way;
  8. sets the barrier to `HandedOff` and calls the handoff.
- **Failure:** any failure before the handoff, including a process that can't be checked, a step that runs out of time or a backup that fails, stops the update and removes the barrier, so every process carries on; uncertainty never counts as a stop.
  A failed backup's reason is shown to the person.

## Installation scope

- An update keeps the app's identity, its install location and scope, and its data directories, unless an explicit migration changes them.
- A fresh Windows install goes to the current user's `%LOCALAPPDATA%\Programs\<slug>`, and an existing installation for all users may need elevation.
- An unclear scope never silently chooses another installation, and an installer's failure never permits downgrading a database or clearing an uncertain launch barrier.
